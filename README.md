# RTG 高精度自动定位系统工程实施手册

---

## 一、项目背景

针对传统定位方案在港口复杂环境下存在精度不足、成本高及适应性差等痛点，本项目引入高精度 GNSS 差分定位技术。通过"基站 + RTG 接收端"架构，为 RTG 大车/小车提供实时、高频、精准的定位数据，以有效支撑自动化调度、大车纠偏及作业安全防护需求。

---

## 二、核心需求

为保障 RTG 自动化作业的精准度与稳定性，系统需满足以下核心要求：

- **全方位定位输出**：实时输出 RTG 大车/小车的绝对位置、运行速度及相对偏移量。
- **高精度技术指标**：平面定位精度达到 ±30mm，高度定位精度达到 ±50mm，且数据刷新率不低于 10Hz。
- **灵活适配机制**：支持堆场坐标系现场标定及标定数据复用，确保定位数据与电子地图高度匹配，无缝适配多堆场作业切换。
- **极高系统可靠性**：具备故障容错与丢星补偿能力，确保系统实现 7×24 小时连续、稳定运行。

---

## 三、坐标系统与定位基准

### 3.1 双坐标系融合

系统必须实时处理两种坐标系之间的转换：

- **WGS84 经纬度系统**：接收机获取的原始定位数据 `(Lat, Lon, Alt)`。
- **堆场局部坐标系 (LYCS)**：每个堆场拥有独立的物理原点 `(0, 0, 0)`，下发给 PLC 的数据须转换为每个堆场内的坐标。

### 3.2 RTG 专用坐标系定义

针对单机作业，定义以下局部参考系：

- **大车基准**：以跑道中心线为参考，偏向堆场内为负，偏向堆场外为正。
- **小车基准**（遵循笛卡尔右手坐标系）：
  - **原点**：以小车位置值为 0 的点作为坐标轴原点。
  - **X 轴**：沿 RTG 小车轨道运行的数值增大方向为正。
  - **Z 轴**：竖直向上方向为正。

## 四、硬件架构与通信链路

### 4.1 接收机与天线配置（3 机 6 天线）

整机共 **3 台双天线 GNSS 接收机、6 根物理天线**；中控按 **3 路 UDP 数据流** 接入（见 `config/system.yaml`），不是 6 路独立流。

#### 单机双天线（定位 + 定向）

每一台双天线接收机内部通常为：

| 天线角色 | 作用 | 中控可见数据 |
|----------|------|-------------|
| **主天线（定位 / Rover）** | RTK 位置 | NMEA **GGA** → `lat/lon/alt` |
| **副天线（定向 / Heading）** | 与主天线构成基线 | **PASHR / GPTRA / PTNL** 等 → `heading/roll/pitch` |

定向天线**一般不单独上报经纬度**，航向由接收机根据两天线基线解算后写入姿态语句。`src/driver/gnss_receiver.py` 将同一 UDP 包内的 GGA 与姿态句合并为一帧 `GnssRaw`；`fusion_node` 用 GGA 做 EKF 位置量测，若有双天线姿态则**直接覆盖**航向/横滚/俯仰。

#### 整机布局与软件映射

| 部位 | 接收机 | 物理天线（同包双 GGA） | UDP 端口 | `role` |
|------|--------|------------------------|----------|--------|
| **大车左** | 1 台 | A1（主）+ A2（副），沿纵向基线 | 9001 | `gantry_a1` |
| **大车右** | 1 台 | B1（主）+ B2（副），沿纵向基线 | 9002 | `gantry_a2` |
| **小车** | 1 台 | 小车两端各 1 根 | 9003 | `trolley` |

端梁四角布局（俯视）：

```
        电气房侧              柴油机侧
   A1(左列)  B1(右列)    A2(左列)  B2(右列)
   └ gantry_a1 (9001) ┘   └ gantry_a2 (9002) ┘
```

- **大车**：接收机1 (`gantry_a1`) 双天线 A1(电气房侧主) + A2(柴油机侧副) 各配独立杆臂，解算两个作业点 L-Point；汇总 L-Point 为两侧均值。不再用跨距推算另一侧作业点。
- **小车**：一台双天线接收机；GGA 为**主天线（定位）**相位中心，副天线位置由主天线坐标 + 航向/姿态旋转的**基线向量**推算（`solver_node._solve_trolley`），两端杆臂见 `config/vehicle_params.yaml` 的 `trolley.antenna_c1/c2`。
- **前端 `ant1`–`ant6`**：仅为物理角色标签（存后端 `vehicle_configs.antennas`），**不决定** UDP 端口；路由以 `system.yaml` 的 `role` 为准。

#### 联调模拟

`tests/20260407_gnss_mock/run_gnss_simulators.py` 可同时向 9001/9002/9003 推送三路 NMEA 日志，对应上述三台接收机，详见该目录下 `GNSS_SIMULATOR_README.md`。

- **大车 (Gantry)**（摘要）：解算 **L-Point** 与航向/横滚/俯仰。
- **小车 (Trolley)**（摘要）：解算小车在 RTG 坐标系下的位置及两端天线坐标。

### 4.2 通信拓扑

| 链路 | 协议 | 说明 |
|------|------|------|
| 内部通信 | UDP/IP（以太网） | 接收机与边缘计算终端之间 |
| 外部通信 | Socket TCP（小端模式） | 工控机与 PLC 之间，帧率 ≥ 10Hz |

## 五、数学解算模型：L-Point 刚体变换

系统不直接使用天线坐标，而是通过"中转站"逻辑将坐标还原到地面作业点位。

### 5.1 静态参数说明

在解算前，必须在系统内录入车辆的物理几何参数：

| 参数 | 含义 |
|------|------|
| `L_arm` | 杆臂向量：天线相位中心相对于地面左侧作业对齐点 (L-Point) 在 RTG 局部坐标系下的 3D 偏移矢量 `(dx, dy, dz)` |
| `H` | 标称高度：天线相位中心到地面的垂直设计距离 |
| `W_span` | 跨距：左右门腿物理中心线的水平距离 |

### 5.2 L-Point 解算公式

为消除因车体倾斜导致的定位偏差，采用三维刚体旋转投影模型计算 L-Point 的世界坐标 `P_final`：

```
P_final = P_gps − R · L_arm
```

**参数说明：**

| 符号 | 含义 |
|------|------|
| `P_gps` | GNSS 接收机输出的实时三维天线位置 `(Xg, Yg, Zg)` |
| `L_arm` | 预设的 3D 杆臂补偿矢量 |
| `R` | 姿态旋转矩阵，由欧拉角构建：`R = Rz(ψ) · Ry(θ) · Rx(φ)` |

### 5.3 姿态角定义

1. **横滚角 (Roll, φ)**：绕 RTG 前后行驶轴（X 轴）旋转，反映 RTG 因地面不平导致的**左右倾斜**。
2. **俯仰角 (Pitch, θ)**：绕 RTG 左右门腿横向轴（Y 轴）旋转，反映 RTG 因轨道起伏导致的**前后倾斜**。
3. **航向角 (Heading, ψ)**：绕垂直轴（Z 轴）旋转，定义 RTG 在堆场中的**行驶朝向**。

### 5.4 首车全场 + 换车 3 点校准（推荐业务模型）

**空间标准**：RTK 手持打的各贝位真值为唯一标准；RTG 解算（经本车刚体）可能与 RTK 不一致，校准记录的是 **偏差**，不是把 RTG 坐标当作标准。

**每台车**：进场前须完成 **静态参数**（`L_arm`、`H`、`W_span`、天线布局），用于天线 → 作业点的刚体变换。RTG-001 与 RTG-002 静态不同，**不可共用**。

| 阶段 | 车辆 | 动作 |
|------|------|------|
| 场地真值 | — | RTK 逐贝建图 → `survey_points`（mapping） |
| 校准1 | 首车 A（如 RTG-001） | **全场** RTK 贝位：记录 A 的解算输出相对 RTK 的逐贝数据 |
| 校准2 | 换车 B（如 RTG-002） | B 的静态 + **仅 3 个** RTK 贝位：求验 **B→A 的坐标转换** `M` |
| 作业 | B | `P_B→场` ≈ `M` × `P_B`，再 **复用 A 在各贝位的全场标定/修正** |

**校准2 前 3 个贝位在干什么？（先转成 001，再用第 3 点验 M）**

| 优先级 | 作用 |
|--------|------|
| **主** | 三对「B 解算点 `P_B` ↔ A 底图同贝点 `P_A`」→ 求车际刚体 **M**，使 `P_A ≈ M × P_B`，**继承 A 全场逐贝表** |
| **辅** | **第 3 贝**：用 M 预测第 3 点，与 `P_A` 比残差，判断 M 是否可靠 |

**平移、旋转怎么来的？**（与 `BVehicleCalibrator` / SVD 一致）

- 平面刚体只有 **3 个未知数**：ΔX、ΔY、Δθ。
- **两对非共线点**即可确定：比较贝 1→贝 2 向量在 B 与 A 中的**方向差**得 Δθ；再用贝 1 对齐得 **(ΔX, ΔY)**。
- **第 3 对**用于冗余校验（残差过大需重打），不是「每个贝一个矩阵」。

**最终输出（概念）：**

```
P_作业 ≈ 套用(A 在贝位 k 的标定) ∘ M × P_B解算
```

> **实现状态**：后端 `finalize(verify)` 写入 `matrix` + `source_vehicle_id`；中控启动时 `GET /api/yard/map` 加载 **M 与参考车全场表**，作业时 `solver_node` 执行 **M 变换 + 贝间残差插值**（见 `PROJECT_SUMMARY.md`）。

### 5.5 首车全场约 40 贝：目的与贝位间精度

**40 个固定贝位不是「每贝一个矩阵」**，而是首车在每台停靠贝记录：

- **RTK 真值**（`ref`，场地标准）
- **001 解算作业点**（`measured`，经本车 `L_arm` 等刚体变换）
- **残差** `delta = measured − ref`（001 可与 RTK 整体偏差，表中是**偏差场**）

`finalize` 后形成全场 **残差修正底图**（`vehicle_bay_transforms` 的 `delta_*`，换车场景另存 `yard_map.json` 中的 **M**），供作业在各贝位套用；**连点成线**，不是 40 个孤立点。

**核心问题：40 贝之外的空白行驶区，如何仍保持约 ±3 cm？**

答案：**40 贝参与构建全场误差趋势，但空白区不靠「再打一个点」**，而靠下列 **四重机制** 联合：

1. **全场统一基础投影**  
   WGS84→堆场 LYCS（`YardTransform`）全场 **一套**、连续；大车任意位置都有大体正确的局部坐标。

2. **残差补丁 + 贝间插值**  
   各贝存有平面与高程残差（`vehicle_bay_transforms` 的 `delta_lat/lon/alt`，中控换算为局部米制）。行驶在贝 5 与贝 6 之间时，`solver_node` 按到邻近贝的**物理距离线性插值**过渡残差，平滑补偿路面起伏、轮胎变形等**系统性**误差。

3. **高频 L-Point 刚体投影（≥10Hz）**  
   全程实时：`P_final = P_gps − R·L_arm`，用 Roll/Pitch/Heading 消除天线杠杆效应；**不限于** 40 个停靠时刻。

4. **EKF 惯导融合**  
   `fusion_node` 融合 GNSS 与 IMU：GNSS 锚定绝对位置，IMU 抑制多径/遮挡引起的跳变，保证贝位间轨迹连续平滑。

```text
空白区定位 ≈ 统一投影(大体坐标)
           → 前后贝插值残差补丁
           → 高频刚体消动态倾斜
           → EKF 平滑
```

## 六、核心功能与解算逻辑

### 6.1 大车定位输出

- **双中心输出**：分别反馈左侧接收机（A1+A2）与右侧接收机（B1+B2）各自 L-Point 距堆场原点的坐标。
- **纠偏原始数据**：实时输出四个门腿中心点相对跑道中心线的偏移量。
- **速度反馈**：大车值增大方向速度为正，减小为负。

### 6.2 小车定位解算

- **相对位置输出**：输出小车两端 GNSS 天线在 RTG 坐标系下的实时 *X* / *Y* / *Z* 坐标。
- **实际行程**：计算小车距离轨道起始点的实际运行距离。
- **安装补偿**：程序支持对小车 2 根天线的安装位置进行数据补偿，消除因安装空间受限导致的结构性偏差。
- **速度定义**：小车沿轨道运行数值增大方向为正，反之为负。

## 七、工程实施流程（与 Web 前后端对齐）

### 步骤① RTK 场地真值（Mapping）

1. **测绘对象**：堆场原点、各贝位 (Bay) 中心线（及可选磁钉）。
2. **操作规范**：RTK 固定解下采集，写入 `survey_points`（`point_type=mapping`）。
3. **含义**：建立 **场地空间标准**；与具体 RTG 无关。

### 步骤② 车体静态测量（VehicleConfig）

1. **每台 RTG 独立录入**：杆臂 `L_arm`、标称高度 `H`、跨距 `W_span`、天线角色。
2. **含义**：定义 **该车** 天线 → 作业点的刚体几何；001 与 002 必须分别测量。

### 步骤③ 场地车辆校准（Calibration）

**校准1 — 首车（如 RTG-001）**

1. 001 完成步骤② 后，开到与 RTK **相同贝位编号**。
2. **全场逐贝**（如约 40 贝）对比「001 解算输出 vs RTK」，写入 `vehicle_bay_transforms`（`delta = 解算 − RTK`）。
3. `finalize` 标记 `completed`。目的见 **§5.5**：建立全场 **误差趋势修正底图**，供作业与换车继承；001 可以与 RTK 对不上，表中记录的是 **偏差场**。
4. 作业与贝间行驶时，结合 §5.5 四重机制（投影 + 插值补丁 + 高频刚体 + EKF）保证空白区精度。

**校准2 — 换车（如 RTG-002）**

1. 002 完成 **自己的** 步骤②。
2. 仅在 **前 3 个 RTK 贝位** 停车采点：每贝一对 **002 解算** 与 **001 底图同贝坐标**（非仅对 RTK），求解 **002→001** 的 `M`；第 3 贝做 **M 残差校验**（见 §5.4）。
3. 通过后 **复用 001 全场逐贝数据**，无需 002 再扫全部贝位；`finalize` 时写入 `M` 与 `source_vehicle_id`（如 RTG-001）。

**校准3 — 同车再次进场**

已 `completed` 的车辆可直接作业；若改贝位需重新采点并 `finalize`。

### 步骤④ 正常作业（Dashboard / 中控解算）

实时 GNSS/IMU → 本车刚体 → 堆场坐标；结合车际 `M` 与首车全场标定（目标架构）对准各贝位。

### 附录：中控运维工具

- `tools/simulator.py`：无硬件时模拟 GNSS/IMU。
- `tools/diagnostic.py`：配置、端口、后端 API、yard_map 检查。
- RTK 建图与逐贝校准统一在 **Web 前端**（Mapping / Calibration）经后端 API 入库。

## 八、软件部署指南（Ubuntu 21.04）

### 8.1 系统优化

- **实时内核补丁**：安装 `rt-preempt`，确保解算任务的实时性（响应时间 ≤ 100ms）。
- **时间同步**：使用 `chrony` 配合 GPS PPS 信号，确保系统时钟微秒级对齐。

### 8.2 模块化部署

| 模块 | 功能 |
|------|------|
| `driver_node` | 解析 NMEA 报文及接收机专有格式数据 |
| `fusion_node` | 运行卡尔曼滤波 (EKF)，融合 IMU 与 GNSS 信号 |
| `solver_node` | 执行姿态投影、L-Point 变换及 `M` 矩阵修正 |
| `bridge_node` | 负责与 PLC 通信，下发 JSON/UDP 指令报文 |

### 8.3 丢星补偿（IMU 融合）

- **惯导补位**：GNSS 信号短时间中断（< 10s）时，利用内置 IMU 进行位姿推算，偏差需 < 250mm。

## 九、常见工程误差消除

1. **全场残差底图与贝间插值**：首车全场校准形成逐贝 `delta_*`（含高程 `delta_alt`）；行驶在贝位之间时按距离插值过渡（§5.5）。
2. **动态高度修正**：高程残差包含在 `delta_alt` 插值结果中，经 `solver_node` 补偿（`lpoint_solver` 可选 `delta_z` 参数）。
3. **姿态平滑**：`fusion_node` EKF 融合 IMU，过滤机械震动引起的航向与位置跳变。
4. **自动跨堆场切换**：`yard_manager` 识别当前堆场，加载对应原点、底图与车际 `M`。
